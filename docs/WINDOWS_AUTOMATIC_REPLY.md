# Windows 自动回复：与 Mac 完整对齐

目标是适配 [Mac 自动回复](AUTOMATIC_REPLY.md) 的全部功能：新入站自动生成并提交文字回复，包括既有 Codex 对话绑定、忙闲交接、范围与预算、人设和署名、授权申请、独立记录核对及停止撤权。读取、草稿或人工提交只算中间进度，不能算 Windows 自动回复完成。仅推进 Windows，Mac 作为实现与历史证据参考。

当前新独立服务尚未整体准入。旧 Mac 自动回复实现也不能通过恢复旧令牌直接用于新架构；以下列出需要移植的机制与 Windows 实际证据，不宣称产品已经可用。

## 功能对齐与验收清单

| 功能 | 复用的 Mac 思路 | Windows 当前进度与待办 |
| --- | --- | --- |
| 选择已有 Codex 对话 | `codex_bridge.py` 官方元数据与 `thread_router.py` 生命周期 | 现有公共实现可参考；新 authority 的登记、路由及 Windows 命令调用待接通 |
| 忙碌排队与原对话恢复 | 未知状态不视为空闲；受信任事件交接，用户任务优先 | 新服务调度尚未接通，不把新建临时对话当作已有对话绑定完成 |

| 全部或指定私聊 | 排除群、公众号及系统会话；新联系人单独核验 | 新服务所有者范围登记及目录刷新待接通 |
| 时长、次数及不限模式 | 内存会话、双时钟；不限仍派生短时单次子权限 | 新服务会话与任务派生待接通，重启不得恢复授权 |

| 永久防重放 | 在任何可能提交前保存尝试，不确定不重发 | Windows NT 相对独占创建与写穿透/刷盘已实现；并发仅一成功、刷盘失败仍留标记的实际文件测试通过 |
| 独立数据库核对 | 精确全文、本人 sender、出站方向、非零 server_id；不改原 Unknown | 新服务的 Windows 发送后观察待接通，不能用 UI 气泡代表数据库或送达证据 |

原功能范围仍为文字回复，不自动发送附件，也不加入支付、朋友圈或账号管理。Windows 必须逐项完成实际接线与适当验收，不能把 Mac 记录或公共模块存在视为 Windows 已通过。

## 本轮 Windows 原生接线

`AuthorityNavigation` 在 Windows 使用有界线程读取匿名管道，替代不支持这些管道的 `select`。继续沿用 Mac 的顺序：helper 发出 ready → 核对真实映像和进程 birth → 可信控制器登记 handler → 生成精确 action 证明 → 交给原生 helper。发送响应丢失保留 Unknown，原任务不重试。

`wechat-uia.exe --authority-v2` 新增分离的草稿暂存、精确比较及单次提交路径。原生侧通过独立 authority C ABI 预检，暂存前认领，最终提交前两次比较输入并单次认领；提交仍不构成送达证明。该路径没有 owner 签发工具或旧证明回退，尚未接入自动会话。搜索导航当前明确拒绝未资格路径，不能用于自动选聊。

`NativeCachedDraftWitness` 直接复用 Mac 缓存见证的数据结构和判定顺序，改用 `NativeDatabase.navigation` 的固定原生操作；Python 不接收密钥或执行通用 SQL。唯一精确缓存、新鲜搜索、会话切换后的缓存消费、双时钟与窗口固定共同形成收件人见证。已用实际 SQLCipher 加密合成库验证正常转换、重复草稿、歧义搜索、用户草稿变化、过期与撤权；未读取真实设备草稿，也未完成自动控制器接线。Windows 原生输入的精确比较只返回元数据，使用 `status.read` 与数据库正文读取的 handler 分开。

2026-10-18 的新实机检查只读取 UIA 结构：4 个节点均为 Other，无 Edit/Button/List，未获取正文、点击、输入或发送。这与 Mac 曾遇到的无可访问聊天控件问题类似，需要继续移植主窗口导航及缓存见证思路。当前 UIA 分阶段实现不能单独解决该设备问题；不使用 OCR、注入或捕获保护绕过来把它标为通过。

参考与正式 Windows 构建均已编译 helper；实际原生子进程完成 ready、真实 birth 登记及无效证明拒绝，没有 UI 动作。桥、管道、尝试标记及新增缓存见证合计 16 项定向测试通过，不包含成功微信发送。最终全量 502 项发现、470 执行通过、32 平台/链接权限跳过（65.567 秒），四项原先仅 Mac 执行的桥接测试已在 Windows 执行。完整回归与最新总状态分别见 [STATUS](STATUS.md) 和 [平台状态](../README.md#一眼看清当前状态)。
